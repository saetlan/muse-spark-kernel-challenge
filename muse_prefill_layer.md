### What the research established (sources in the agents' reports; key ones cited)
- **No library does NVFP4 (group-16 E4M3) W4A16 on sm_90**: CUTLASS SM90 mixed input requires `group_size % TileK == 0` (`sm90_mma_tma_gmma_rs_warpspecialized_mixed_input.hpp:484`, ex. 55 README), TileK ≥ 32; Machete same (`machete_mainloop.cuh:648`, int4/int8 only); FlashInfer/TRT-LLM SM90 W4A16 MoE = MXFP4 group 32 UE8M0 (`moe_gemm_kernels.h:196`), NVFP4 W4A16 only on SM100 (CuTe DSL). NVFP4 → MXFP4 isn't lossless. ⇒ **own kernel**.
- **wgmma RS** (A from registers): BF16 `m64nNk16`, N = 8…256 step 8; per-warp A layout = `mma.m16n8k16`'s (row = 16w + g + 8·((i>>1)&1), k = 2q + (i&1) + 8·(i>>2); CUTLASS `ALayout_64x16`). ⇒ **MoE M11's fragment shuffle carries over**. One k16 instruction = exactly one NVFP4 scale group per row; each thread needs 2 scales per k16. A registers must not be touched until `wgmma.wait_group` covers the MMA ⇒ double-buffer decoded fragments. No `trans-a` in RS form (A K-major, fine). B smem descriptor: 64-bit (addr>>4, LBO, SBO, base offset, swizzle 128B/64B/32B) (PTX §9.7.17.5.1.2.2).
- **TMA**: `cp.async.bulk` 1D needs no tensor map (16 B aligned/sized); tensor maps via `cuTensorMapEncodeTiled`; multicast to a cluster; `cp.async.bulk.prefetch.L2`; **no row gather on Hopper** (gather4 is sm_100). Device-side `tensormap.replace` exists (sm_90a).
- **setmaxnreg** (24–256, step 8, per warpgroup; e.g. 24/240/240 for 1 producer + 2 consumer WGs); `fence.proxy.async` before wgmma/TMA read generic-proxy smem writes; mbarrier expect_tx pipelines; PDL works under graph capture (programmatic edge; needs `cudaLaunchKernelEx`); clusters work in graphs.
- **Issue budget**: 4 schedulers × 1 instr/clk/SM; LOP3/shift/IMAD 64/clk/SM, FP32 FMA 128, MUFU 16, f32→bf16 cvt 16 (!), smem 128 B/clk/SM. Per warp, `m64nNk16` occupies N/2 issue slots ⇒ decoding 8 values (~10 int ops + 4 HMUL2) per thread per k16 is ~15–25% of slots at N = 128, more at N = 64 ⇒ token tiles ≥ 64–128 keep decode hidden. Weight streaming balances MMA at ~62 tokens per tile.
- **Decode trick for one HMUL2 per pair**: decode E2M1 bits as value·2^-126 (bf16), multiply by a prepare-time bf16 scale `s·2^118` (exact for every E4M3 scale: 2^-9·2^118 … 448·2^118 < 2^128) ⇒ value·s·2^-8, exact; epilogue × 2^8 × global. Lossless scale repack (E4M3 → bf16 is exact; CUTLASS requires ≥ 2-byte scales anyway).
- **Attention (FA3 @ f89bc23)**: FP8 hdim ≤ 64 uses 192×160 tiles, 3 MMA WGs + producer WG, P in registers; **page size 1 ⇒ cp.async gather path** (TMA only if page % 160 == 0 and not local), pack_gqa forced on, `num_splits` heuristic gives 2 splits at b = 1 / q 753 (plus a combine kernel), none elsewhere; `pack_gqa`/`sm_margin` don't help. **FA3 runs at 59–62% of the MUFU (exp) floor on every full-attention shape**, and its time ≈ 1.1 × (MMA + MUFU): softmax and GEMM barely overlap. Sliding layers are overhead-bound (20–45% of floor). FA4's tricks work on Hopper in principle: polynomial exp2 on the FMA pipe (degree 2 suffices for FP8 P: 0.21% max rel err), lazy rescale; f32x2 packed FMA is Blackwell-only. Possible extra cost: FP32→E4M3 conversion may run at 16/clk/SM (unverified).
- **Grouped-GEMM scheduling (GPU MODE winner's worklog, DeepGEMM, Hazy)**: persistent static schedule, groups sorted by descending M (LPT), device prefix-sum tile table, weight-stationary CTAs (one N-block, stride over M tiles), swapped operands so the variable side is MMA-N, L2 swizzle groups, TMA multicast pairs; dynamic queues help only with uneven work (+14% Hazy).
- **DeepGEMM** has SM90 BF16 grouped GEMMs (`m_grouped_bf16_gemm_nt_contiguous/_masked`, since v2.1.0) — a BF16 baseline candidate for v2's 16K path; no mixed input on SM90.
- **CUTLASS ex. 113** (Hopper grouped GEMM with fused gated activation, pingpong, cluster 1×2) and **ex. 63** (weight prefetch into L2 under PDL) exist; FlashInfer's `cute_dsl_fused_moe_bf16` (SM90: cp.async gather producer WG + wgmma consumer WGs, SwiGLU, fused finalize) is a CuTe DSL template.
