## Problem-specific checklist (on top of the shared one)

- No `prepare()` here: `kernel_fn(data)` only. Build (`load_inline`, Triton) and launch every kernel once at import time or on an eager call, never first inside a capture.
- Follows the shared `CLAUDE.md` (rules, file conventions, the method) and `docs/SOURCES.md` (read Nov 3 ~21:30 UTC). This problem has no `prepare()`: labs wrap `kernel_fn` and run once on the first eager call (after the warm-up), so the timed path stays the submission's byte for byte (`attention/local/make_lab.py`).
- `sh attention/local/presubmit.sh <files>` before every run: header, shared lint, py_compile, and `attention/local/emulate_v1.py --quick` (a CPU emulation of v1's three kernels, program by program, run through the judge's own `check_implementation` on 13 cases including dp, page 64, kv_scale 1/64, dist edges/coherent and verify).
- Also in presubmit: `check_dispatch.py` (the SGLang fallback `sglang_path` and its helpers must equal `baseline.py`'s by AST after renames; `kernel_fn` must route each scored class as `OURS` says; mutation-checked) and `mutation_test.py` (8 planted bugs in the emulated kernels, each must fail the judge's checker on the case set: window edge, window start, causal, head pairing, RoPE sign, last key, merge rescale, cache scale). Cases added because mutations survived: per-row verify window edges (`window_rows_case`, page 1 and 64) and a 40K bs1 full case whose maximum sits in the merge's last chunk (`late_key_case`). Two mutations are equivalent by construction and excluded: dropping v_scale and the merge's denominator rescale (the RMSNorm after attention cancels any per-(token, head) constant).
- **CUDA register arrays are never indexed with a lane-dependent value** (lane, g, t4, hl, warp, tid): it forces the array into local memory (AF20). `attention/local/check_cuda_registers.py` enforces it (mutation-checked on the pre-fix A5b line); every lab prints `cudaFuncGetAttributes` local bytes and flags non-zero.
- Presubmit also runs, for `attention/local/cuda_{dec2,fused,ver}.py`: the register check, clang syntax, and the quick register-level emulators (~90 s in all).
- CUDA strings: `attention/local/check_cuda_syntax.py <file> <VAR>` (clang -fsyntax-only, sm_90a, stubs copied to `attention/local/cuda_stubs/` and extended with `__ldg(const int*)`, `Tensor::numel`). L2's gather kernel passes.
- Sources review (`docs/SOURCES.md`, six links): **Inference Engineering** roofline: every shape compared with TASK.md floors (AF2, AF6, AF9); **vLLM** CUDA-graph rules: no host syncs, no value-dependent sizes or branches, buffers allocated per call from shapes only, warm-up outside capture (lint + checklist 4); **SGLang**: fallback = baseline call for call (check_dispatch); FA3 semantics we reproduce (window (2047, 0), causal inside the verify block, 5.473/8 scale, FP8 cache with descales) checked against `reference.py`; **GPU MODE** judging: all work inside the timed call, nothing cached from inputs, scratch allocated per call; the lab lives only in check-run files. Not yet read for attention ideas: FlashInfer / TensorRT-LLM XQA decode kernels for page size 1 (A15).
- Kernels compile and load on the first non-captured `kernel_fn` call (`_warm_up`: every scored variant on tiny dummies), not at import, so CUDA isn't initialised while the harness is still setting up. Runtime ints that vary with lengths (`max_pages`, `nsplit`) are `do_not_specialize`, so dummy and real calls share one compiled variant.
- Triton 3.8.0 source checked (scratchpad copy): `triton.language.extra.libdevice` is a module (allowed as a global in jit code; imported as `import … as libdevice` so the shared lint sees a module); `do_not_specialize` accepts names (`jit.py:803`); `tl.rsqrt/exp2/trans/cdiv/maximum/full` exported.
- Tests include `heads dp` (128 q / 16 kv heads), page 64, kv_scale 1/64, a 1,048,576-token context and `dist edges`: nothing may assume tp8, page 1 or scale 1.

## Brainstorm B1 (Nov 3 ~22:15 UTC): the road to #1 (3.34×)

Inputs: the updated `CLAUDE.md` (goal #1, research-first, Hopper-specific), the Hopper tuning guide and architecture blog (F47; DSMEM ~7× faster exchange than global, clusters co-scheduled, TMA/bulk copies register-free with mbarrier byte counts), PTX ISA 9.4 (`griddepcontrol` sm_90; `ex2.approx.f16x2` / `.ftz.bf16x2`; `mma.m16n8k32` e4m3; `cp.async.bulk` 1D), research R-A1 (AF12), and our measurements AF2–AF17. What #1 needs is AF16; the two hard parts are scattered-row bandwidth and single-kernel latency.

### What limits us today (measured)
1. Full layers: request size. 64 B halves → ~1.7 TB/s; whole 128 B rows → 3.4 (Triton) / 3.8 (CUDA) random, 4.08 sequential; streaming ceiling 4.49 (AF13, AF10, F20).
2. Sliding layers: 3 launches and ~4 dependent DRAM round trips; merge kernel 1.9 µs; prologue 1.5 µs (AF15).
3. bs1 full: slices too short (latency), merge 4.8 µs (AF15).
4. Verify full (bs16/32 on SGLang today): compute + exponentials as heavy as the memory floor (AF17).

## Brainstorm B6 (Nov 5 ~01:50 UTC): the coordination session's two levers, estimated before building

Request relayed by the coordination session (user, Nov 5 ~01:45: "could we explore … Attention 128-key stages; A22 persistent length-aware split"); evaluate and plan, no spending without the user's go-ahead here.
1. **128-key stages for W3b (Fv16 / Fv32).** Shared memory fits at 4 consumer warpgroups: a 128-key slot is 51.7 KB (Kc 16 KB + Vs 18.4 KB + Vt 16.9 KB), 3 stages 155 KB + Q tiles 16 KB + P tiles 4 × 8 KB + entries 3 KB = 206 KB of 227. ## Brainstorm B7 (Nov 5 ~02:30 UTC): TMA bulk copies for the W3b / UW2 copier (A58), the coordination session's proposal

Relayed with the user's go-ahead to send (not to spend): "the most ambitious untried lever": W3b's copier issuing one 128 B `cp.async.bulk` per K / V row (one lane per row, 4 instructions per lane per stage instead of 32), completion counted by `mbarrier` expect-tx, so the copier waits only on empty slots.
- **What we already know.** AF19 (L5, random 128 B rows of the whole pool): `cp.async.bulk` 128 B + mbarrier reached 3.43 TB/s at best, plain `cp.async` 16 B 3.79, whole-row `ld` 3.79. So TMA per row is not faster per byte than cp.async in isolation; what limits W3b (~2.3 TB/s) is how its copier keeps requests in flight (one or two issuing warps that wait on their own groups), and bulk copies would remove that wait. Step 1 of the proposal (the microbenchmark) is partly answered: random 128 B bulk copies can sustain > 3 TB/s on this H200.
- **Layout constraint.** A 128 B bulk copy writes a row contiguously. W3b's K tile is the no-swizzle K-major canonical layout (a key's four 16 B dim chunks sit LBO = 128 B apart, 8 keys of a core matrix 16 B apart), and the swizzled layouts permute 16 B chunks by row, which a linear bulk copy cannot do. So K must also land row-major in staging (like V) and the transposer warps re-lay it into the canonical tile (16 B moves, no transposition), or Q·K must take K as a register operand. Shared memory: + 9 KB per stage (K staging, pitch 144) → 5 stages fit at 4 consumer warpgroups (≈ 210 KB), not 6.
- **Estimate.** If the copy side reached D3's 3.1 TB/s: Fv16 153 → ~115 µs, Fv32 285 → ~215 µs (+5.5% score); at 3.4 TB/s, ~105 / ~195 µs (+7%), provided the consumers (4 warpgroups, ~0.5 µs per stage per SM measured with no memory traffic in L29) and the transposers (now re-laying K too) keep up. Same copier in UW2 → Sv1 / Sv16. **Cost** ~2.5–3 h (copier with bulk copies + expect-tx, K staging and the transposers' K re-lay, page entries ahead, emulator), **risk** medium-high (expect-tx byte counts, async-proxy ordering between the bulk writes and the transposers' generic reads, ring depth 5). Plan: after W3s (L40), a lab with the TMA copier variant (W3t) on Fv16 / Fv32 directly, since AF19 already shows the copies themselves can go > 3 TB/s; a microbenchmark only if W3t is slow.
